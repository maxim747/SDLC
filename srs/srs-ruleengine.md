## 1. Введение {#1-introduction}

Документ задаёт требования к программной системе RuleEngine – движку обработки вебхуков, который принимает
события от эмулятора, проверяет их по сохранённым JSON-правилам и при совпадении отправляет ответный
POST-запрос на эмулятор или в систему уведомлений. В документе описаны назначение и область применения
продукта, его окружение, верифицируемые требования и способы их проверки.

### 1.1 Назначение документа {#11-document-purpose}

SRS фиксирует, **ЧТО** должна делать система RuleEngine, а не то, как она будет устроена. Документ является
соглашением между заказчиком и разработчиком. Им пользуются: заказчик (проверка того, что система решает его
задачу), разработчик (источник требований для проектирования и реализации), тестировщик (источник критериев
приёмки) и преподаватель (оценка лабораторной работы). Документ ведётся в Git, изменения вносятся через
pull request.

### 1.2 Область применения продукта {#12-product-scope}

Продукт: **RuleEngine**, версия 0.1 (первая версия требований). Это backend-сервис, который автоматически
обрабатывает входящие события эмулятора без ручного анализа. Бизнес-цели:

- **BG-1** – обработка и проверка входящего вебхука от эмулятора не дольше 50 мс;
- **BG-2** – точное сопоставление параметров вебхука с сохранёнными JSON-правилами без ложных срабатываний;
- **BG-3** – гарантированная доставка ответного POST-запроса на эмулятор или в систему уведомлений с
  логированием.

**Входит в продукт:** приём входящих вебхуков, хранение JSON-правил в БД, сопоставление (matching), отправка
POST-запросов, повторные попытки при сбое, журнал событий и доставок, REST API и веб-интерфейс управления
правилами, импорт и экспорт правил, настройка каналов уведомлений.

**Не входит в продукт:** сам эмулятор событий, визуальный (перетаскиваемый) конструктор правил, серверы
Telegram и SMTP, компоненты машинного обучения.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

RuleEngine – новый самостоятельный сервис. Он находится между эмулятором событий (вышестоящая система,
источник вебхуков) и системой уведомлений (нижестоящая система: Telegram, SMTP, Webhook). Состояние хранится
во внешней для сервиса базе данных PostgreSQL. Администратор управляет правилами через REST API и веб-интерфейс.
Владелец продукта – заказчик, роль которого исполняет напарник по лабораторной работе; сопровождение
выполняет команда разработки.

Внутри системы выделены два компонента: **Webhook Receiver** (приём и проверка вебхуков) и **Rule Matcher &
Action Executor** (сопоставление с правилами и выполнение действий).

![Контекстная диаграмма системы RuleEngine](img/context-diagram.png)

### 2.2 Функции продукта {#22-product-functions}

Основные функции (см. также диаграмму вариантов использования):

1. Приём и проверка входящих вебхуков (UC-06).
2. Хранение JSON-правил в БД и управление ими (UC-01).
3. Сопоставление событий с правилами (UC-07).
4. Отправка POST-запросов на эмулятор или в систему уведомлений с повторными попытками (UC-08).
5. Импорт и экспорт правил (UC-02, UC-03).
6. Настройка каналов уведомлений (UC-04).
7. Просмотр журнала событий и доставок (UC-05).

![Диаграмма вариантов использования](img/usecases-diagram.png)

### 2.3 Ограничения продукта {#23-product-constraints}

| ID | Ограничение | Тип |
|----|-------------|-----|
| CON-1 | Система должна быть реализована на TypeScript и Node.js 20 | Внутреннее, обязательное |
| CON-2 | Входящие события поступают только вебхуками по HTTP(S) в формате JSON | Внешнее, обязательное |
| CON-3 | Правила и журнал должны храниться в PostgreSQL 16 | Внутреннее, обязательное |
| CON-4 | Обработка вебхука и проверка правила должны занимать не более 50 мс | Внешнее (требование заказчика), обязательное |
| CON-5 | Система должна поставляться в контейнерах Docker | Внутреннее, обязательное |

Раздел 3 определяет верифицируемые обязательства системы, которые обеспечивают эти ограничения.

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Класс | Описание | Частота работы | Цели |
|-------|----------|----------------|------|
| Администратор | Технический специалист, знающий формат JSON и HTTP | Эпизодически (создание и правка правил, просмотр журнала) | Управлять правилами, настраивать уведомления, разбирать срабатывания |
| Эмулятор событий | Внешняя система | Постоянно, до 100 вебхуков в секунду | Отправлять события и получать ответные запросы |
| Система уведомлений | Внешняя система (Telegram, SMTP, Webhook) | По срабатыванию правил | Получать уведомления |

Интерфейс администратора рассчитан на русскоязычного пользователя; локализация не требуется.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

| ID | Допущение или зависимость | Влияние, если неверно |

| AS-2 | Эмулятор подписывает вебхуки общим секретом HMAC-SHA256 | Придётся заменить механизм аутентификации источника (REQ-SEC-002) |

| AS-5 | На машине развёртывания установлен Docker | Запуск по REQ-INST-001 невозможен |

## 3. Требования {#3-requirements}

Требования сформулированы с ключевым словом «должна» и снабжены уникальными неизменяемыми идентификаторами
вида REQ-[AREA]-[NNN]. Требования связаны с бизнес-целями BG-1 – BG-3 диаграммой требований.

![Диаграмма требований](img/requirements-diagram.png)

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

![Мокап интерфейса управления правилами](img/ui-rule-management.png)

- **ID:** REQ-INT-005
- **Title:** Веб-интерфейс управления правилами
- **Statement:** Система должна предоставлять веб-интерфейс администратора со списком правил (название, источник события, приоритет, статус), поиском по названию, фильтром, кнопками создания, изменения, удаления, включения и отключения правила, а также просмотром истории выполнения выбранного правила.
- **Rationale:** Администратору нужен наглядный доступ к правилам и их срабатываниям без ручных запросов к API (BG-2, BG-3).
- **Acceptance Criteria:** В интерфейсе доступны все перечисленные операции; после создания правила оно появляется в списке; история выполнения показывает время, статус и длительность каждой отправки.
- **Verification Method:** Demonstration
- **More Information:** UC-01, UC-05; рисунок «Мокап интерфейса управления правилами». Условие правила вводится полями формы (поле, оператор, значение); перетаскиваемый визуальный конструктор не входит в проект.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

Система не взаимодействует с физическими устройствами. Требований нет.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

- **ID:** REQ-INT-001
- **Title:** Приём вебхуков по HTTP API
- **Statement:** Система должна принимать входящие вебхуки от эмулятора событий методом POST на конечную точку /webhook в формате JSON (Content-Type: application/json) по HTTPS.
- **Rationale:** Единственный канал получения событий от эмулятора (BG-1).
- **Acceptance Criteria:** POST /webhook с корректным JSON возвращает 202 Accepted; запрос другим методом возвращает 405; запрос с Content-Type, отличным от application/json, возвращает 415.
- **Verification Method:** Test
- **More Information:** UC-06; ограничение CON-2.

- **ID:** REQ-INT-002
- **Title:** Отправка исходящего POST-запроса
- **Statement:** Система должна при совпадении правила отправлять POST-запрос с телом в формате JSON на адрес, указанный в действии правила: на эмулятор событий или в систему уведомлений.
- **Rationale:** Ответное действие – конечный результат работы движка (BG-3).
- **Acceptance Criteria:** При совпадении правила тестовый приёмник получает ровно один POST-запрос на адрес из действия правила; тело запроса соответствует шаблону тела из действия правила.
- **Verification Method:** Test
- **More Information:** UC-08; REQ-FUNC-005.

- **ID:** REQ-INT-003
- **Title:** REST API управления правилами
- **Statement:** Система должна предоставлять REST API (JSON по HTTPS) для создания, чтения, изменения, удаления, включения и отключения правил: GET/POST /rules, GET/PUT/DELETE /rules/{id}.
- **Rationale:** Администратор должен гибко менять правила без правки кода и перезапуска сервиса (BG-2).
- **Acceptance Criteria:** Каждая из операций выполняется запросом к API и возвращает коды 200/201/204 для успешных запросов и 404 для несуществующего правила; изменённое правило применяется к следующему вебхуку без перезапуска.
- **Verification Method:** Test
- **More Information:** UC-01; REQ-FUNC-006.

- **ID:** REQ-INT-004
- **Title:** Интерфейс с базой данных PostgreSQL
- **Statement:** Система должна хранить правила и журнал событий в PostgreSQL версии 16 и обращаться к ней по протоколу PostgreSQL через параметризованные запросы.
- **Rationale:** Правила и журнал должны сохраняться между перезапусками сервиса (CON-3).
- **Acceptance Criteria:** После перезапуска контейнера с сервисом все ранее созданные правила и записи журнала доступны через API.
- **Verification Method:** Test
- **More Information:** Раздел 2.3.

- **ID:** REQ-INT-006
- **Title:** Каналы системы уведомлений
- **Statement:** Система должна поддерживать отправку уведомлений через каналы Telegram (Bot API), SMTP и произвольный Webhook.
- **Rationale:** Заказчик указал три типа получателей уведомлений (BG-3).
- **Acceptance Criteria:** Для каждого из трёх каналов тест с тестовым получателем подтверждает доставку уведомления: сообщение в тестовом чате Telegram, письмо на тестовом SMTP-сервере, POST-запрос на тестовом приёмнике.
- **Verification Method:** Test
- **More Information:** UC-04, UC-08; REQ-FUNC-010.

### 3.2 Функциональные требования {#32-functional}

- **ID:** REQ-FUNC-001
- **Title:** Приём и валидация вебхука
- **Statement:** Система должна при получении вебхука проверять, что тело запроса является корректным JSON-объектом с обязательными полями event.id, event.type и event.source, и отклонять некорректные запросы с кодом 400 и описанием ошибки.
- **Rationale:** Некорректные события не должны попадать в сопоставление и давать ложные срабатывания (BG-2).
- **Acceptance Criteria:** Запрос без поля event.type, запрос с невалидным JSON и пустое тело возвращают 400; корректный запрос возвращает 202.
- **Verification Method:** Test
- **More Information:** UC-06; REQ-INT-001.

- **ID:** REQ-FUNC-002
- **Title:** Хранение правил в JSON
- **Statement:** Система должна хранить каждое правило в базе данных PostgreSQL в виде JSON-документа (поля условия и действия типа JSONB) вместе с названием, приоритетом и признаком включения.
- **Rationale:** Администратор должен гибко менять правила (интервью с заказчиком, BG-2).
- **Acceptance Criteria:** Созданное правило сохраняется в таблице rules; прочитанное по API правило полностью совпадает с созданным; правило с некорректной JSON-структурой не сохраняется и возвращает 422.
- **Verification Method:** Test
- **More Information:** UC-01; REQ-INT-004.

- **ID:** REQ-FUNC-003
- **Title:** Сопоставление вебхука с правилами
- **Statement:** Система должна сопоставлять каждый принятый вебхук со всеми включёнными правилами и определять, какие правила совпали.
- **Rationale:** Основная функция движка – точное сопоставление без ложных срабатываний (BG-2).
- **Acceptance Criteria:** Набор из 20 тестовых событий и 10 правил даёт ожидаемое множество совпавших правил, расхождений нет; отключённое правило не срабатывает ни на одном событии.
- **Verification Method:** Test
- **More Information:** UC-07.

- **ID:** REQ-FUNC-004
- **Title:** Язык условий правил
- **Statement:** Система должна поддерживать в условии правила сравнение значений полей события (в том числе вложенных, через запись event.payload.cpu_percentage) операторами eq, ne, gt, gte, lt, lte, contains, а также объединение условий через and и or.
- **Rationale:** Правилам нужны числовые и строковые условия, например «загрузка процессора выше 95» (BG-2).
- **Acceptance Criteria:** Для каждого оператора есть тест с совпадением и несовпадением; условие по отсутствующему полю даёт несовпадение, а не ошибку обработки.
- **Verification Method:** Test
- **More Information:** UC-07; рисунок «Мокап интерфейса управления правилами».

- **ID:** REQ-FUNC-005
- **Title:** Формирование действия правила
- **Statement:** Система должна при совпадении правила формировать тело исходящего запроса из шаблона действия, подставляя значения полей события вместо меток вида {{event.type}}.
- **Rationale:** Уведомление должно содержать данные события, вызвавшего срабатывание (BG-3).
- **Acceptance Criteria:** Для шаблона {"text": "Событие {{event.type}} от {{event.source}}"} и тестового события тело запроса содержит подставленные значения; метка с несуществующим полем заменяется пустой строкой.
- **Verification Method:** Test
- **More Information:** UC-08; REQ-INT-002.

- **ID:** REQ-FUNC-006
- **Title:** Управление правилами
- **Statement:** Система должна позволять администратору создавать, изменять, удалять, получать список и просматривать отдельное правило.
- **Rationale:** Базовый вариант использования администратора (UC-01).
- **Acceptance Criteria:** Через API и через веб-интерфейс выполняются все пять операций; удалённое правило не возвращается в списке и не срабатывает.
- **Verification Method:** Test
- **More Information:** UC-01; REQ-INT-003, REQ-INT-005.

- **ID:** REQ-FUNC-007
- **Title:** Приоритет и статус правила
- **Statement:** Система должна позволять задавать правилу приоритет (low, medium, high, critical) и статус (активно, неактивно) и применять совпавшие правила в порядке убывания приоритета.
- **Rationale:** Администратор различает важность правил и может временно отключать правила, не удаляя их.
- **Acceptance Criteria:** Два совпавших правила разных приоритетов выполняются в порядке убывания приоритета, что видно по времени записей в журнале; неактивное правило не выполняется.
- **Verification Method:** Test
- **More Information:** UC-01; рисунок «Мокап интерфейса управления правилами».

- **ID:** REQ-FUNC-008
- **Title:** Импорт правил
- **Statement:** Система должна позволять администратору загрузить набор правил из JSON-файла, проверяя структуру каждого правила, и не добавлять ни одного правила из файла, если хотя бы одно правило не прошло проверку.
- **Rationale:** Перенос и массовая загрузка правил между окружениями (UC-02).
- **Acceptance Criteria:** Файл из 10 корректных правил добавляет 10 правил; файл, в котором одно правило некорректно, возвращает ошибку с номером правила и не меняет набор правил в БД.
- **Verification Method:** Test
- **More Information:** UC-02.

- **ID:** REQ-FUNC-009
- **Title:** Экспорт правил
- **Statement:** Система должна позволять администратору выгрузить все правила в JSON-файл в формате, пригодном для импорта по REQ-FUNC-008.
- **Rationale:** Резервное копирование и перенос правил (UC-03).
- **Acceptance Criteria:** Экспорт, за которым следует импорт в чистую базу, даёт набор правил, идентичный исходному.
- **Verification Method:** Test
- **More Information:** UC-03.

- **ID:** REQ-FUNC-010
- **Title:** Настройка уведомлений
- **Statement:** Система должна позволять администратору задавать параметры каналов уведомлений (Telegram: токен бота и идентификатор чата; SMTP: сервер, порт, учётные данные, адрес получателя; Webhook: адрес) и проверять их отправкой тестового уведомления.
- **Rationale:** Администратор должен настраивать получателей без изменения кода (UC-04).
- **Acceptance Criteria:** После сохранения параметров кнопка «Тест» отправляет тестовое уведомление, а при неверных параметрах возвращает понятную ошибку.
- **Verification Method:** Test
- **More Information:** UC-04; REQ-INT-006, REQ-SEC-003.

- **ID:** REQ-FUNC-011
- **Title:** Журнал событий и доставок
- **Statement:** Система должна записывать в журнал каждое принятое событие, результат сопоставления, каждую попытку отправки (номер попытки, код ответа, длительность) и итоговый статус доставки, а администратору – позволять просматривать журнал с фильтрацией по времени, правилу и статусу.
- **Rationale:** Логирование доставки требуется для бизнес-цели BG-3 и разбора инцидентов.
- **Acceptance Criteria:** После теста с одним событием, совпавшим с одним правилом, в журнале присутствуют запись о событии, запись о совпадении и запись о доставке; фильтр по статусу FAILED возвращает только неудачные доставки.
- **Verification Method:** Test
- **More Information:** UC-05; REQ-OBS-001.

- **ID:** REQ-FUNC-012
- **Title:** Обработка события без совпадений и с несколькими совпадениями
- **Statement:** Система должна при отсутствии совпавших правил записывать событие в журнал со статусом NO_MATCH без исходящих запросов, а при нескольких совпавших правилах выполнять действия всех совпавших правил.
- **Rationale:** Движок не должен терять события и должен однозначно вести себя в граничных случаях (BG-2).
- **Acceptance Criteria:** Событие без совпадений: 0 исходящих запросов и запись NO_MATCH; событие, совпавшее с тремя правилами: 3 исходящих запроса.
- **Verification Method:** Test
- **More Information:** UC-07.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

- **ID:** REQ-PERF-001
- **Title:** Время обработки вебхука
- **Statement:** Система должна принять входящий вебхук, сопоставить его с JSON-правилами и принять решение о совпадении не более чем за 50 мс.
- **Rationale:** Автоматическая обработка событий без ручного анализа возможна только при малой задержке (BG-1).
- **Acceptance Criteria:** При нагрузке 100 вебхуков в секунду и 1000 активных правил 99-й перцентиль времени от приёма вебхука до решения о совпадении по результатам теста из 10 000 вебхуков не превышает 50 мс (время исходящего запроса не учитывается).
- **Verification Method:** Test
- **More Information:** UC-06, UC-07; ограничение CON-4.

- **ID:** REQ-PERF-002
- **Title:** Пропускная способность
- **Statement:** Система должна обрабатывать не менее 100 входящих вебхуков в секунду на одном экземпляре сервиса.
- **Rationale:** Эмулятор может отправлять пачки событий; сервис не должен накапливать очередь (BG-1).
- **Acceptance Criteria:** Нагрузочный тест 100 вебхуков/с в течение 5 минут завершается без отказов (ответов 5xx) и с очередью необработанных событий нулевой длины в конце теста.
- **Verification Method:** Test
- **More Information:** Допущение AS-3.

- **ID:** REQ-PERF-003
- **Title:** Время отклика API управления
- **Statement:** Система должна отвечать на запросы REST API управления правилами не более чем за 500 мс при наличии до 1000 правил.
- **Rationale:** Работа администратора в интерфейсе не должна страдать от задержек.
- **Acceptance Criteria:** При 1000 правил в БД 95-й перцентиль времени ответа на GET /rules и POST /rules не превышает 500 мс.
- **Verification Method:** Test
- **More Information:** REQ-INT-003.

#### 3.3.2 Безопасность {#332-security}

- **ID:** REQ-SEC-001
- **Title:** Аутентификация администратора
- **Statement:** Система должна требовать аутентификацию для всех запросов REST API управления правилами и веб-интерфейса и отклонять запросы без действительного токена доступа с кодом 401.
- **Rationale:** Правила определяют, какие уведомления получат люди; их изменение посторонним недопустимо (BG-2).
- **Acceptance Criteria:** Запрос к /rules без токена и с просроченным токеном возвращает 401; с действительным токеном – 200.
- **Verification Method:** Test
- **More Information:** UC-01.

- **ID:** REQ-SEC-002
- **Title:** Аутентификация источника вебхуков
- **Statement:** Система должна принимать вебхуки только с действительной подписью HMAC-SHA256 в заголовке X-Signature, вычисленной по телу запроса общим секретом, и отклонять остальные запросы с кодом 401.
- **Rationale:** Нужно исключить ложные события от посторонних источников (BG-2).
- **Acceptance Criteria:** Вебхук с верной подписью принимается (202); вебхук без подписи и с неверной подписью получает 401 и не попадает в сопоставление.
- **Verification Method:** Test
- **More Information:** REQ-INT-001.

- **ID:** REQ-SEC-003
- **Title:** Защита секретов
- **Statement:** Система должна хранить секреты (токен Telegram-бота, пароль SMTP, общий секрет подписи вебхуков, ключ подписи токенов) в переменных окружения или в зашифрованном виде и не выводить их в журналы и ответы API.
- **Rationale:** Утечка секретов позволила бы отправлять сообщения от имени системы.
- **Acceptance Criteria:** Поиск значений тестовых секретов по журналам, ответам API и дампу таблицы rules не находит их в открытом виде.
- **Verification Method:** Inspection
- **More Information:** REQ-FUNC-010.

- **ID:** REQ-SEC-004
- **Title:** Защита каналов и входных данных
- **Statement:** Система должна принимать подключения только по TLS версии 1.2 или выше, ограничивать размер тела входящего запроса значением 1 МиБ и использовать параметризованные SQL-запросы.
- **Rationale:** Защита от перехвата данных, перегрузки большими запросами и SQL-инъекций.
- **Acceptance Criteria:** Подключение по TLS 1.1 отклоняется; запрос размером 2 МиБ возвращает 413; строка "'; DROP TABLE rules; --" в названии правила сохраняется как текст и не изменяет схему БД.
- **Verification Method:** Test
- **More Information:** REQ-INT-001, REQ-INT-004.

#### 3.3.3 Надёжность {#333-reliability}

- **ID:** REQ-REL-001
- **Title:** Повторная отправка при сбое
- **Statement:** Система должна при неудачной отправке исходящего POST-запроса (сетевая ошибка, таймаут 5 с или код ответа 5xx) повторять отправку до 3 раз с экспоненциальной задержкой 1, 2 и 4 секунды.
- **Rationale:** Заказчик потребовал гарантированную доставку ответного запроса (BG-3).
- **Acceptance Criteria:** Тестовый приёмник, возвращающий 503 два раза подряд и затем 200, получает три запроса, а доставка получает статус DELIVERED; приёмник, всегда возвращающий 503, получает 4 запроса (первичный и 3 повторных), доставка получает статус FAILED.
- **Verification Method:** Test
- **More Information:** UC-08; интервью с заказчиком, таблица 3.2.

- **ID:** REQ-REL-002
- **Title:** Защита от дублей событий
- **Statement:** Система должна игнорировать повторно полученное событие с тем же event.id в течение 24 часов, не выполняя действий правил повторно, и записывать такое событие в журнал со статусом DUPLICATE.
- **Rationale:** Эмулятор может повторять отправку вебхука, а повторные уведомления вредят получателям (BG-2, BG-3).
- **Acceptance Criteria:** Два одинаковых вебхука подряд вызывают одно исходящее действие; второй возвращает 200 и получает в журнале статус DUPLICATE.
- **Verification Method:** Test
- **More Information:** REQ-FUNC-001, REQ-FUNC-011.

- **ID:** REQ-REL-003
- **Title:** Поведение при недоступности БД
- **Statement:** Система должна при недоступности PostgreSQL отвечать на входящие вебхуки кодом 503 с заголовком Retry-After и автоматически возобновлять приём после восстановления соединения без перезапуска.
- **Rationale:** Эмулятор может повторить отправку позже, поэтому событие не должно теряться молча (BG-3).
- **Acceptance Criteria:** При остановленной БД POST /webhook возвращает 503; через 30 секунд после запуска БД запрос возвращает 202 без перезапуска сервиса.
- **Verification Method:** Test
- **More Information:** REQ-INT-004.

#### 3.3.4 Доступность {#334-availability}

- **ID:** REQ-AVAIL-001
- **Title:** Доступность сервиса
- **Statement:** Система должна быть доступна не менее 99,5 % времени в календарный месяц и автоматически перезапускаться в случае аварийного завершения процесса.
- **Rationale:** Эмулятор отправляет события постоянно, длительная недоступность приводит к потере автоматизации.
- **Acceptance Criteria:** При принудительном завершении процесса контейнер перезапускается и принимает вебхуки не позднее чем через 30 секунд (политика restart: unless-stopped); расчёт доступности по журналу проверок /health даёт не менее 99,5 %.
- **Verification Method:** Test
- **More Information:** REQ-OBS-001.

#### 3.3.5 Наблюдаемость {#335-observability}

- **ID:** REQ-OBS-001
- **Title:** Журналирование и проверка состояния
- **Statement:** Система должна писать структурные JSON-журналы с полями время, уровень, event_id, rule_id, номер попытки и длительность этапа, а также предоставлять конечную точку GET /health, возвращающую состояние сервиса и соединения с БД.
- **Rationale:** Без телеметрии невозможно доказать выполнение BG-1 и BG-3 и разобрать сбой.
- **Acceptance Criteria:** Для тестового события в журнале присутствуют записи для каждого этапа с одним event_id; GET /health возвращает 200 при работающей БД и 503 при остановленной.
- **Verification Method:** Inspection
- **More Information:** REQ-FUNC-011.

### 3.4 Соответствие стандартам {#34-compliance}

- **ID:** REQ-COMP-001
- **Title:** Форматы данных и протокол
- **Statement:** Система должна использовать JSON по RFC 8259 для всех входящих и исходящих данных и HTTP по RFC 9110 (методы и коды состояния).
- **Rationale:** Единые стандартные форматы обеспечивают совместимость с эмулятором и системой уведомлений.
- **Acceptance Criteria:** Автоматическая проверка схемой и инспекция показывают, что все ответы API – валидный JSON, а коды состояния соответствуют RFC 9110.
- **Verification Method:** Inspection
- **More Information:** Раздел 1.4.

- **ID:** REQ-COMP-002
- **Title:** Формат даты и времени
- **Statement:** Система должна хранить и передавать дату и время в формате RFC 3339 (ISO 8601) в UTC.
- **Rationale:** Однозначность времени событий и срабатываний в журнале.
- **Acceptance Criteria:** Все поля времени в ответах API и журнале соответствуют шаблону YYYY-MM-DDThh:mm:ssZ.
- **Verification Method:** Test
- **More Information:** REQ-FUNC-011.

- **ID:** REQ-COMP-003
- **Title:** Лицензии зависимостей
- **Statement:** Система должна использовать только сторонние библиотеки с лицензиями MIT, Apache-2.0 или BSD.
- **Rationale:** Исключение юридических рисков при распространении проекта.
- **Acceptance Criteria:** Отчёт инструмента проверки лицензий (npm license-checker) не содержит библиотек с другими лицензиями.
- **Verification Method:** Analysis
- **More Information:** Раздел 2.3.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

- **ID:** REQ-INST-001
- **Title:** Запуск одной командой
- **Statement:** Система должна запускаться вместе с PostgreSQL 16 командой docker compose up из корня каталога проекта на Windows, Linux и macOS с установленным Docker.
- **Rationale:** Простой запуск сокращает затраты на развёртывание и приёмку.
- **Acceptance Criteria:** На чистой машине с Docker команда docker compose up поднимает оба сервиса, GET /health возвращает 200 не позднее чем через 60 секунд.
- **Verification Method:** Demonstration
- **More Information:** REQ-BUILD-001.

- **ID:** REQ-INST-002
- **Title:** Настройка через переменные окружения

- **Rationale:** Одинаковый образ используется в разных окружениях без пересборки.
- **Acceptance Criteria:** Изменение значения переменной в .env и перезапуск контейнера меняют поведение без пересборки образа; в репозитории нет реальных секретов.

- **Acceptance Criteria:** Две сборки из одного коммита на разных машинах дают образы с одинаковым набором версий зависимостей.
- **Verification Method:** Test
- **More Information:** REQ-INST-001.

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

- **ID:** REQ-POC-001
- **Title:** Доказательство концепции по скорости
- **Statement:** До полной реализации должен быть выполнен прототип, который принимает вебхук, сопоставляет его с 1000 правилами и отправляет POST-запрос, с измерением времени обработки.
- **Rationale:** Проверить достижимость цели BG-1 (50 мс) раньше, чем будет написана вся система.
- **Acceptance Criteria:** Отчёт о прототипе содержит измеренное 99-е перцентильное время обработки; при превышении 50 мс решение по кешированию правил и структуре данных пересматривается.
- **Verification Method:** Test
- **More Information:** REQ-PERF-001.
